# Using the REST API from Home Assistant

Everything the web UI does — scanning, pairing, connecting, disconnecting, changing per-device
settings — is a REST call, and Home Assistant can make every one of those calls itself. That means
you can connect a speaker from an automation, a script, a dashboard button, or a schedule.

The most common reason to want this: you have **Auto Reconnect turned off** (so the add-on stops
competing with a phone for the same speaker), but you still want the speaker to connect at 7am, or
when you press a button, or when an automation fires.

**No port forwarding, no API token, no extra configuration.** Home Assistant can already reach the
add-on over its internal network.

---

## Quick example

Add this to `configuration.yaml`, restart Home Assistant, and you have a `rest_command` you can
call from anywhere:

```yaml
rest_command:
  bt_audio_connect:
    url: "http://REPLACE-WITH-YOUR-HOSTNAME:8099/api/connect"
    method: post
    content_type: "application/json"
    payload: '{"address": "AA:BB:CC:DD:EE:FF"}'
```

Call it from an automation:

```yaml
automation:
  - alias: "Connect kitchen speaker at 7am"
    triggers:
      - trigger: time
        at: "07:00:00"
    actions:
      - action: rest_command.bt_audio_connect
```

You need two values: **your hostname** and **your speaker's MAC address**. The add-on generates the
whole block for you with both already filled in — see below.

---

## The interactive API reference

The add-on ships its own Swagger UI. Open it from the add-on's web UI:

**BT Audio → Settings (top right) → API Reference**

It is also at `/api/docs` if you prefer to navigate directly.

What you get there:

- **Every endpoint**, with the exact request and response shape, all validation rules (allowed
  values, numeric ranges), and what each error status means.
- **Try it out** — run any call straight from the browser against your real hardware. This is the
  fastest way to check what an endpoint returns before you wire it into an automation. It works
  through the Home Assistant sidebar, no separate login.
- **A "Call this API from Home Assistant" panel** at the top. Pick an endpoint and one of your
  paired devices, and it produces the exact `rest_command` block — **your** hostname, **your**
  device's MAC address — with a copy button.

> ⚠️ **Try it out is not a sandbox.** It runs against your actual Bluetooth hardware. `POST
> /api/forget` really does unpair a device, and `POST /api/restart` really does restart the add-on.

## How Home Assistant reaches the add-on

Add-ons sit on Home Assistant's internal Supervisor network, and each one gets a DNS name that
Home Assistant Core can resolve. Nothing is exposed to your LAN, and no authentication token is
involved.

The hostname is the add-on's full slug with underscores replaced by hyphens:

| Add-on | Hostname |
| --- | --- |
| Bluetooth Audio Manager | `<repo-hash>-bluetooth-audio-manager` |
| Bluetooth Audio Manager (Dev) | `<repo-hash>-bluetooth-audio-manager-dev` |

The port is always **8099**.

`<repo-hash>` is generated by Home Assistant when you add this repository, so it differs between
installations. **You cannot guess it — you have to look it up.**

### Finding your hostname

**Easiest:** open **API Reference** in the add-on (Settings → API Reference). The panel at the top
shows your hostname and builds the config block around it.

**Alternative:** go to **Settings → Add-ons** and click the add-on. The browser URL contains the
full slug:

```text
http://homeassistant.local:8123/hassio/addon/a1b2c3d4_bluetooth_audio_manager/info
                                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

Replace every `_` with `-` to get the hostname:
`a1b2c3d4_bluetooth_audio_manager` → `a1b2c3d4-bluetooth-audio-manager`

> **The hostname changes if you reinstall from a different repository**, and the stable and dev
> add-ons have different hostnames. If your automations stop working after reinstalling,
> re-check this value first.

## Recipes

All of these assume you have substituted your own hostname for `YOUR-HOSTNAME`.

### One command, any device

Rather than a separate command per speaker, define one that takes the address as a variable:

```yaml
rest_command:
  bt_audio_connect:
    url: "http://YOUR-HOSTNAME:8099/api/connect"
    method: post
    content_type: "application/json"
    payload: '{"address": "{{ address }}"}'

  bt_audio_disconnect:
    url: "http://YOUR-HOSTNAME:8099/api/disconnect"
    method: post
    content_type: "application/json"
    payload: '{"address": "{{ address }}"}'
```

Then pass the address when you call it:

```yaml
actions:
  - action: rest_command.bt_audio_connect
    data:
      address: "AA:BB:CC:DD:EE:FF"
```

### Connect on a schedule

The original use case — an amplifier that powers on when a Bluetooth device connects, with Auto
Reconnect left off the rest of the time:

```yaml
automation:
  - alias: "Power on amp for morning radio"
    triggers:
      - trigger: time
        at: "07:00:00"
    actions:
      - action: rest_command.bt_audio_connect
        data:
          address: "AA:BB:CC:DD:EE:FF"
      # Give the speaker a moment to come up before playing anything
      - delay: "00:00:10"
      - action: media_player.play_media
        target:
          entity_id: media_player.kitchen_speaker
        data:
          media_content_id: "http://your-radio-stream"
          media_content_type: music

  - alias: "Release amp at bedtime"
    triggers:
      - trigger: time
        at: "23:00:00"
    actions:
      - action: rest_command.bt_audio_disconnect
        data:
          address: "AA:BB:CC:DD:EE:FF"
```

### A dashboard button

```yaml
type: button
name: Connect Kitchen Speaker
icon: mdi:bluetooth-audio
tap_action:
  action: perform-action
  perform_action: rest_command.bt_audio_connect
  data:
    address: "AA:BB:CC:DD:EE:FF"
```

### Fix a stuck connection

Sometimes a device reports as connected but no audio flows — a "zombie" connection. There is a
single endpoint that disconnects and reconnects in one go:

```yaml
rest_command:
  bt_audio_force_reconnect:
    url: "http://YOUR-HOSTNAME:8099/api/force-reconnect"
    method: post
    content_type: "application/json"
    payload: '{"address": "{{ address }}"}'
```

### Check whether it actually worked

`POST /api/connect` returns HTTP 200 even when the speaker did not come up — the JSON body tells
you the outcome. Capture it with `response_variable`:

```yaml
script:
  connect_speaker_and_verify:
    sequence:
      - action: rest_command.bt_audio_connect
        data:
          address: "AA:BB:CC:DD:EE:FF"
        response_variable: result
      - if:
          - condition: template
            value_template: "{{ result.content.connected }}"
        then:
          - action: notify.persistent_notification
            data:
              message: "Speaker connected."
        else:
          - action: notify.persistent_notification
            data:
              message: >-
                Speaker did not connect — it is probably powered off or out of range.
```

`response_variable` gives you `status` (the HTTP code), `content` (the parsed JSON body), and
`headers`.

### Expose device state as a sensor

To react to a speaker connecting or disconnecting, poll `/api/devices`:

```yaml
rest:
  - resource: "http://YOUR-HOSTNAME:8099/api/devices"
    scan_interval: 30
    sensor:
      - name: "Kitchen Speaker Bluetooth"
        unique_id: kitchen_speaker_bluetooth
        value_template: >-
          {% set d = value_json.devices
             | selectattr('address', 'eq', 'AA:BB:CC:DD:EE:FF')
             | first | default(none) %}
          {{ 'connected' if d and d.connected else 'disconnected' }}

      - name: "Kitchen Speaker Signal"
        unique_id: kitchen_speaker_signal
        unit_of_measurement: dBm
        value_template: >-
          {% set d = value_json.devices
             | selectattr('address', 'eq', 'AA:BB:CC:DD:EE:FF')
             | first | default(none) %}
          {{ d.rssi if d is not none and d.rssi is not none else 'unknown' }}
```

Every sensor under one `resource:` shares a single poll, so adding more costs no extra requests.

> **Don't use `json_attributes_path: "$.devices[0]"` here.** `/api/devices` returns *all* devices
> and the order is not stable, so a fixed index can pull attributes from a different speaker than
> the one your `value_template` selected — giving you a sensor whose state and attributes disagree.
> Select by address in each template instead, as above.

Each device also reports `has_transport`. A device with `connected: true` but
`has_transport: false` is in the zombie state described above — a useful thing to alert on.

## Turning off Auto Reconnect

If you are driving connections from automations, you probably want the add-on to stop reconnecting
on its own. Two ways:

**In the UI:** BT Audio → Settings → App Settings → turn off **Auto Reconnect**.

**Via the API**, if you want to toggle it from an automation:

```yaml
rest_command:
  bt_audio_auto_reconnect:
    url: "http://YOUR-HOSTNAME:8099/api/settings"
    method: put
    content_type: "application/json"
    payload: '{"auto_reconnect": {{ enabled | lower }}}'
```

```yaml
actions:
  - action: rest_command.bt_audio_auto_reconnect
    data:
      enabled: false
```

This takes effect immediately — no restart needed. It also stops any reconnect attempt already
under way, rather than waiting for the current backoff loop to give up.

The setting persists across restarts. With Auto Reconnect off, the add-on does not reconnect
stored devices when it starts — after an update, a Home Assistant restart, or a host reboot — so a
speaker you deliberately left free for a phone stays free. Devices that are already connected are
untouched: the add-on only stops *initiating* connections, it never tears one down.

## Security

The API has **no authentication**. That is deliberate and safe in this context: the Supervisor
network is internal to Home Assistant and not reachable from your LAN or the internet.

> **Do not add a `ports:` entry to the add-on configuration** to "make it easier to reach." That
> would publish an unauthenticated API on your local network, where anything on your LAN could
> unpair your devices or restart the add-on. The internal hostname is the supported access path,
> and it already works from Home Assistant without any exposure.

## Troubleshooting

**`Platform error rest_command - Error requesting data`, or the call times out**

Almost always a wrong hostname. Re-check it in **API Reference**, remembering that stable and dev
have *different* hostnames and that reinstalling from a different repository changes the hash.

**HTTP 400 — "Invalid Bluetooth address format"**

The address must be six colon-separated hex pairs: `AA:BB:CC:DD:EE:FF`. Hyphens are not accepted.
In YAML, always quote it — unquoted it can be misread.

**HTTP 200 but `"connected": false`**

The command reached the add-on and the attempt ran, but the device did not come up. Usually
powered off, out of range, or already connected to something else (a phone). Check the add-on
Logs view.

**"Device not responding" / "already in progress"**

These come from BlueZ. The add-on translates them into readable text; the full detail is in the
add-on's Logs view.

**Verify the add-on is reachable at all**

The simplest end-to-end check needs no automation — call the health endpoint from
**Developer Tools → Actions**:

```yaml
action: rest_command.bt_audio_health
```

with

```yaml
rest_command:
  bt_audio_health:
    url: "http://YOUR-HOSTNAME:8099/api/health"
    method: get
```

A `status` of 200 means Home Assistant can reach the add-on and the hostname is right.

## All available endpoints

The complete, always-current list — with schemas, validation rules, and examples — is in the
add-on's own **API Reference** (`/api/docs`). A summary of what is available:

| Area | What you can do |
| --- | --- |
| Devices | List, scan, pair, connect, disconnect, force-reconnect, forget |
| Device settings | Idle mode, keep-alive, MPD instance and port, AVRCP toggle |
| App settings | Auto Reconnect, reconnect interval and backoff, scan duration |
| Adapters | List adapters, switch the active one, restart the add-on |
| Audio | List Bluetooth PulseAudio sinks with volume, sample rate, codec info |
| Status | Health, version, adapter info, combined state for polling |
| Diagnostics | Recent logs, MPRIS/AVRCP diagnostic dump |
| Real-time | WebSocket event stream at `/api/ws` |

The machine-readable OpenAPI spec is at `/api/openapi.json` — import it into Postman, or generate
a client from it.
